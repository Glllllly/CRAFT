# Pipeline存储资源治理 One Page
核心问题：Pipeline资源增速超预期


# 一、背景与目标
## 背景
在成本优化大背景下，资源申请难度增加，预算与用户活跃度相关。Pipeline资源需求量及增速持续加大，业务视角缺乏清晰的资源使用模型与规划，导致资源不足时业务面临风险。本项目期望明确资源使用模型，以清晰占用来源、支持逻辑优化与异常识别，同时为资源扩容提供理论依据。

## 目标
- 建立Pipeline资源使用模型与监控体系，定期记录核心存储资源的空间及CPU利用率。
- 梳理重度依赖的主要流量来源，监控流量波动。
- 明确用户增长与资源使用的关系，优化至线性相关。
- 优化逻辑以减缓资源增速、降低使用量：
  - 解决某Redis实例扩容瓶颈，降低存储使用量若干TB，未来保留多倍扩容空间。
  - 旧版本管道下线，预估节省约1TB存储。
  - 备份数据拆分至缓存数据库，预估节省约2TB存储。
  - 某Abase实例放缓空间增速，提升同空间支持用户数量多倍。
  - 消息更新清理旧数据，预估节省若干TB存储。
  - 非活跃实体及冷用户数据写入优化。
  - 解除部分存储依赖，优化容灾降级逻辑，支持主备流量灵活切换。


# 二、业务现状
## 现状概述
Pipeline核心依赖两个KV存储实例（Abase实例A和Redis实例B），扩容后峰值使用率如下：

| 存储实例       | 总容量 | 峰值使用量 | 峰值使用率 | 分片数 |
|----------------|--------|------------|------------|--------|
| Abase实例A     | XX TB  | XX TB      | XX%        | XX     |
| Redis实例B     | XX TB  | XX TB      | XX%        | XX     |

### Abase实例A占用概述
- 核心数据表每周增长约0.5-0.8TB及0.15TB，增速随业务波动。
- 主要增长来自数据包（Command=6），需重点优化。

### Redis实例B占用概述
- 每周增长约总容量的0.8%，主要占用来自备份降级数据（约40%）及单管道数据（约34%）。


# 三、优化方向
## 资源使用量化及监控
- 建立存储资源与上游调用量监控体系。

## 降低存储流量
- 联合上游优化冗余流量，重点针对Command=6场景。
- 聚合特定类型内容，减少重复数据存储。
- 优化消息拆包逻辑，减少因属性差异导致的冗余存储。
- 过滤非活跃实体及冷用户的数据写入。

## 内部资源优化
- 迁移备份降级数据至支持LRU策略的Redis集群，缓解存储压力。
- 压缩大尺寸数据包，降低空间占用。
