# Note

# Step1:行业场景选择
圈定行业场景
我们初步把行业场景分为「业务场景」和「职能场景」，业务场景包含但不限于产品、研发、生产、销售、市场、运营、设计等众多部门，职能场景为行政、人事、财务、法务、IT这五大场景。
在圈定场景时，可以结合以下因素考虑：
根据行业Knowhow，判断该行业客户从业务出发所需求的系统类型
根据Base功能边界，判断Base是否适合解决这一类系统问题
尽量扩大客户规模边界，即某些大客户会选择自研/外采三方系统来解决，但中小客户会选择Base进行搭建
电商和生活服务要拆开

打标中发现的可以简化/优化的方式
人员A
如果没有一个业务系统的说明书，理解业务系统要花费很多时间，还不一定能理解全面。比如：某轻型管理系统，里面有较多的同步、http接口工作流，这可能涉及外部的日程、审批等，但是没有相应说明，较难理解各个字段的作用
通过试标注发现耗时挺长，而且标注的时候，要多次回到原始表格查看，通过表格上下文综合判断。考虑是不是可以直接基于原始表格存副本去改动，对于任务不需要的字段、表格直接删除，不再区分P0、P1、不需要，直接留下需要的，可以修改、新增。这样既可以省去人工整理标注表格的时间，也可以提升标注的效率
表格中有一些隐藏的字段，是容易在标注过程中忽略的。可以考虑全部打开，避免标注遗漏
人员B
如果遇到P0-但需要修改，是不是应该再给出细分修改的点，比如是名字有问题还是内容有问题，或者直接写在备注里也行
需要设置自动化流程，如果表格/仪表盘我已经选了不需要，那么后面的字段可以自动打标为不需要
说明需要有，且越细致越方便

人员A
标注需要关注的问题：
公式无法运行，语法错误，需要修改。且修改后语法没有问题，也需要验证是否正确计算结果。可能存在文本差异，例如某表格中的状态字段，不同表述的值不统一
countif不支持嵌套，之前的公式有语法问题
还有计算进度值的时候，出现了分母为0的情况
状态相关公式可能有问题，但是不太能确定，比如：如果任务状态为已完成、已取消，是否算已完成还是进行中？
某业务表格问题：仪表盘的名称不好，两个同类图表都叫通用名称，但下钻后其实是分类型的

两个同类通知，感觉可以删掉一个

标注效率提升思路讨论：
标注的过程中通篇理解数据表、工作流、公式、仪表盘，从大面上判断哪些要留，哪些删除，命名是否合理？不去检查具体公式、工作流数据是否准确
具体公式、工作流是否准确，留个后续标注解决，是否OK？
人员B

需要关注的问题：
有一些表格仅有视图没有原表，是否需要检查原表信息
感觉看上去会更大面一点，对于必要性和非必要性的界限需要再认知上明确一些——业务sense
如果手头有更好的表格，可以直接在更好的表格上进行修改
字段顺序可以顺便做处理，包括字段分组
如果修改字段，那么字段内的内容也要做1-2个字段内容mock
智能化：如果有关联关系，需要尽量按照关联关系填写
可以多给一些样张进行选取，先做一轮样张质量的判断
还是比较难想到需要增加的字段，基本还是基于表格内已有信息做创作（除非是多给到几个模板互相借鉴）
时间：
感觉一张表格应该可以控制在1H以内完成，如果对该业务比较熟悉且表格质量没有特别多的细节问题，估计可以在45Min完成
